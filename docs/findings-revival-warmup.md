# 調査: 復活の判定を最初の N 回だけ止めると何が変わるか

実施日: 2026-11-12 / 計測コード: `00aa0aa`（全実行 `repo_dirty: false`）/ 4 スレッド / **品質専用の診断**（日中に実行。時間は記録していない）

[findings-revival.md](findings-revival.md) の結論 2 では、復活の標的の 36〜40%（指数 1.0）が「平均の 0.1 倍より大きいブロブの唯一の重心」だった。判定時の質量は平均の 0.03〜0.06 倍で、ブロブの真の大きさよりかなり小さい。そこで「学習の初期には EMA 質量が真の大きさに追いついていない（遅れ）」と推測した。本調査はこの推測を確かめる。

## 方法

- `diagnose_revival.py --warmup-checks N` を使った。最初の N 回の復活判定では、公式の `_choose_splits` を呼ばずに「分割なし」とする（`emv/revival.py`）。
  - **これは本リポジトリの改変で、公式のアルゴリズムではない。** 公式コード（`faiss-src/`）は変更していない。
  - 飛ばした判定では乱数を消費しない。このため、それ以降の寄贈元の抽選は公式の実行とずれる。
  - N = 0 は公式の挙動そのものである。今回の N = 0 と閾値 0 の 120 回の学習は、以前の `rev_imb10` / `rev_imb13` / `rev_sep` と test MSE・復活数・未被覆ブロブがすべて一致した。
  - 飛ばした判定でも、閾値未満の重心の数は記録する（`checks.csv` の `skipped=True` の行）。復活が一度も起きない状態での推移が分かる。
- N = 1, 2, 4, 8 を使った。1 回の学習の判定回数は 9 / 15 / 14 回（1 / 3 / 10 エポック）である。N = 8 は、1 エポックなら最後の 1 回だけ判定する極端な場合である。
- その他の条件は findings-revival.md と同じにした。
  - d=64、Medium（n=200,000、k=1,024）で、imbalanced（指数 1.0、1.3）と separated を使った。
  - 5 シード、e-means++、1 / 3 / 10 エポック、閾値 0.1。比較として閾値 0 と Lloyd++25 も実行した。
- レポート: `reports/rev_warmup_imb10/`、`reports/rev_warmup_imb13/`、`reports/rev_warmup_sep/`。

## 結果 1: 止めても、閾値未満の重心は減らない

N = 8 の実行では、最初の 8 回の判定で復活が一度も起きない。その間の「質量が閾値（平均の 0.1 倍）未満の重心の数」の推移を示す（5 シードの中央値）。

| データ | エポック | 判定 0（学習の 7〜10% 時点） | 判定 3 | 判定 7（53〜82% 時点） | 判定 8 で復活を解禁した直後の判定 9 |
|---|---|---|---|---|---|
| imbalanced 1.0 | 1 | 177 | 172 | 155 | （判定 8 が最後） |
| imbalanced 1.0 | 3 | 126 | 149 | 140 | 13 |
| imbalanced 1.0 | 10 | 95 | 108 | 94 | 10 |
| imbalanced 1.3 | 1 | 360 | 393 | 383 | （判定 8 が最後） |
| imbalanced 1.3 | 3 | 307 | 343 | 338 | 45 |
| imbalanced 1.3 | 10 | 254 | 281 | 279 | 43 |
| separated | 3 | 73 | 93 | 101 | 0 |

- 遅れが原因なら、学習が進むにつれて閾値未満の重心は減るはずである。実際には、学習の半分以上が過ぎても横ばいか、むしろ増えた。
- 解禁した判定 8 では、閾値未満の重心のほぼすべてが一度に復活させられた（復活数は「寄贈元の数」が上限）。

公式の実行（N = 0）でも、時間がたつと標的の内訳が変わるかを調べた。「唯一の重心で、ブロブが小さくない」標的の割合を、判定の番号ごとに集計した。

| データ | 判定 0 | 判定 1 | 判定 2〜3 | 判定 4〜7 | 判定 8 以降 |
|---|---|---|---|---|---|
| imbalanced 1.0 | 32% | 38% | 46% | 43% | 44% |
| imbalanced 1.3 | 14% | 15% | 26% | 28% | 24% |

- 後の判定ほど割合は下がらず、むしろ上がった。
- 判定 2 以降のこれらの標的のうち、それより前の分割で標的または寄贈元になっていたのは 10%（指数 1.0）／ 21%（指数 1.3）だけだった。直接の連鎖では大半を説明できない。

## 結論（この条件の範囲に限る）

1. **「初期の EMA 質量の遅れ」が主因だという推測（findings-revival.md 結論 2）は支持されなかった。**
   - 復活を止めたまま学習しても、閾値未満の重心は減らなかった。指数 1.0 では学習の 82% 時点でも 94〜155 個、指数 1.3 では 279〜383 個が閾値未満のままだった。
   - 公式の実行でも、後の判定ほど「小さくないブロブの唯一の重心」が標的になる割合は下がらなかった。
   - 標的の重心は、時間をかければ追いつくのではなく、そのブロブの点をずっと少ししか受け取っていない。なぜ大きさが平均の 0.1 倍以上あるブロブの唯一の重心が、平均の 0.1 倍未満の質量しか持たないのかは、本調査では分かっていない。ブロブの点の多くが別の重心に割り当てられている可能性があるが、未確認である。
     - **追記: 続く調査で確認した**（[findings-revival-noise.md](findings-revival-noise.md)）。取りこぼしではなかった。閾値のすぐ上のブロブの質量が、少ない点数によるばらつきで一時的に閾値を下回り、その時点で標的になる。
2. **それでも、判定を遅らせるほど imbalanced での劣後は縮んだ（N に対して単調）。**
   - 指数 1.0 の N = 8 では閾値 0 とほぼ同じ MSE になった（10 エポックで 103.52 対 103.13、到達 4/5 対 5/5）。
   - 指数 1.3 では N = 8 でも閾値 0 との差が大きく残った（96.46 対 84.71）。後の判定でも、標的の約 5 割は閾値未満の小さいブロブの唯一の重心だった（標的が単独 60% のうち、ブロブが小さくないのは 11%）。これは「閾値未満の真のクラスタを、閾値どおりに復活の対象にする」ことによる劣後で、遅れでは説明できない。
   - 遅らせると効く理由は特定できていない。遅らせると、復活の延べ数（指数 1.0 で 281 → 109）、同じ重心の再復活、標的に占める「小さくないブロブの唯一の重心」の割合（39% → 11%）がいずれも減った。どれが効いているかは分けられていない。さらに N = 8 では、復活させた子が学習の残り（40% 以下）しか動けない。
3. **separated では、判定を遅らせるほど復活の利益が減った。**
   - 10 エポックの MSE は 104.99（公式）から 113.39（N = 8）に悪化した。未被覆ブロブも 64 から 80 に増えた。
   - 復活の利益は、主に学習の初期の復活から来ている。「最初の数回を止める」は imbalanced の劣後を減らす代わりに separated の利益を削る。どちらにも効く設定ではない。
4. 本調査の改変（N > 0）は、仕組みを調べるためのものである。公式の既定値についての主張や、推奨設定として読まないこと。

## 再現コマンド

```bash
P="uv run python diagnose_revival.py --profile medium --threads 4 --warmup-checks 0 1 2 4 8"
$P --dataset imbalanced --imbalance-exponent 1.0 --run-name rev_warmup_imb10
$P --dataset imbalanced --imbalance-exponent 1.3 --run-name rev_warmup_imb13
$P --dataset separated --run-name rev_warmup_sep
```

本文の表のうち、レポート（`report.md`）にない集計がある。判定ごとの閾値未満の数、判定番号ごとの標的の内訳、到達シード数である。これらは生の `results/<run>/checks.csv`・`events.csv`・`runs.csv`（Git 管理外）から集計した。
