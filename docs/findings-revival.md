# 調査: クラスタ復活は何を動かしているか

実施日: 2026-11-12 / 計測コード: `71f51c7`（全実行 `repo_dirty: false`）/ 4 スレッド / **品質専用の診断**（日中に実行。時間は記録していない）

[findings-imbalanced.md](findings-imbalanced.md) で、不均衡データでの e-means の劣後の主因はクラスタ復活（`unused_threshold`、既定 0.1）だと分かった。ただし次の 3 点が未検証だった。

- 結論 2: 閾値を下回る真のクラスタが 0% の指数 1.0 でも劣後するのはなぜか（「1 つの真のクラスタを 2 つの重心が分け合う」ことで発動すると推測していた）。
- 結論 7: 復活は学習の初期に集中しているか（発動時期は未記録）。
- 結論 8: 小さいバッチほど判定の機会が増えて復活が多くなるか。

## 方法

`diagnose_revival.py` で、公式 `NumpyEmeans` のサブクラス（`emv/revival.py`）を通して学習した。サブクラスが包むのは、5 更新ごとの復活の判定 `_choose_splits` だけである。公式の処理を先に実行し、その後でモデルの状態を読むだけにした。乱数は消費せず、状態も変えない。公式コードは改変していない。

- **記録しても学習は変わらない。** テスト（`tests/test_revival.py`）に加えて、本調査の 117 回の学習すべてで、以前のベンチマーク（`q_imb_exp10`、`q_imb_exp10_thr0`、`medium_t4`、`q_imb_thr0`、`q_sep_thr0`、`q_d2imb_*`）と test MSE・復活の延べ数がビット単位で一致した。Lloyd++25 の参照値も一致した。
- **真のブロブ（データを生成した正規分布の塊）との対応。** 人工データの生成を再現して、真の中心と確率を得た（`data.synthetic_truth`）。出力は `synthetic_data` とビット単位で同一である。各重心について、最も近い真の中心を「その重心のブロブ」とした。
- 条件は e-means++（Lloyd++ と同じ k-means++ 初期重心）、1 / 3 / 10 エポック、閾値 0.1（公式の既定）と 0（復活なし）。
  - d=64: Medium（n=200,000、k=1,024）の imbalanced（指数 1.0 と 1.3）と separated を、5 シードで実行した。
  - d=2: imbalanced（指数 1.3）を、quality 則と throughput 則それぞれ 3 シードで実行した。

### 記録した量（定義）

| 量 | 定義 |
|---|---|
| 標的 | 判定時に質量が「閾値 × 平均質量」未満で、復活させられた重心（分割の子の置き場所になる） |
| 寄贈元 | 分割された重心（質量に比例して抽選。公式の処理） |
| 質量 / 平均 | 判定時の EMA 質量 ÷ 全重心の平均質量 |
| ブロブの大きさ / 平均 | 真のブロブの確率 × ブロブ数（1 = 平均的な大きさ。閾値 0.1 未満が「小さい真のクラスタ」） |
| 共有ブロブ上 | 判定時に、標的のブロブを最寄りとする重心が 2 つ以上ある |
| 単独 | 判定時に、標的がそのブロブを最寄りとする唯一の重心である（復活させると、そのブロブから重心がなくなる） |
| 発動時点 | 判定を行った更新の番号 ÷ 学習全体の更新回数 |
| 未被覆ブロブ / 未被覆の質量 | 学習後の重心のどれからも最寄りとされないブロブの数と、その真の確率の合計 |

## 結論（この条件の範囲に限る）

1. **復活は、真のブロブに置かれた重心を引き剥がし、すでに重心のある大きなブロブへ移す。その結果、学習後に重心のないブロブが増える。**
   - 寄贈元は、平均の 4〜5 倍（指数 1.0）〜 23〜36 倍（指数 1.3）の大きなブロブ上にある。その 62〜82% は、すでに 2 つ以上の重心があるブロブだった。
   - 学習後の未被覆ブロブは、復活なしの 266〜283（指数 1.0）／ 438〜453（指数 1.3）から、復活ありでは 352〜382 ／ 691〜711 に増えた。未被覆の質量も 1.3〜2.3 ポイント増えた。
   - 復活なしの未被覆は Lloyd++25（267 ／ 437）とほぼ同じである。MSE の差（findings-imbalanced.md の結論 1）は、この配置の差と対応する。
2. **結論 2（指数 1.0 でも劣後する理由）は、2 つの経路で説明できる。**
   - 標的の 60〜64% は、他の重心と同じブロブを最寄りとしていた（推測していた「分け合い」）。
   - 残りの 36〜40% は、そのブロブの唯一の重心だった。しかも、そのブロブは小さくなかった（ブロブの大きさ / 平均 ≥ 0.1、標的全体の中央値で約 0.35）。
   - 判定時の標的の質量は平均の 0.03〜0.06 倍で、ブロブの真の大きさよりかなり小さかった。学習の初期（単独の標的の発動時点の中央値は全体の 14〜20%）には、EMA 質量が真の大きさに追いついていないと考えられる。小さいブロブにはバッチあたり数点しか入らないので、その抽出のばらつきも効く。ただし、どちらがどれだけ効いているかは分けていない。
   - 指数 1.3 では、単独の標的のうち 15〜19 ポイントが閾値以上のブロブ、残り（28〜36%）が閾値未満の小さいブロブ上だった。
3. **結論 7（発動時期）を確認した。復活は学習の最初の 4 分の 1 に集中する。**
   - d=64 では、イベントの 58〜87% が最初の 25% の更新で起き、後半は 1〜12% だった。
   - エポック数を増やしても延べ数が増えない理由は、更新回数がほぼ変わらないためである。バッチ則がエポック数とともにバッチを大きくするので、判定回数は 1 / 3 / 10 エポックで 9 / 15 / 14 回にとどまる。
   - 同じ重心が繰り返し復活させられる例も多い（イベントの 21〜31%。separated では 17〜54%）。
4. **結論 8（小さいバッチほど復活が多い）を確認した。ただし「判定の機会」に比例するわけではない。**
   - d=2 の quality 則は、判定回数が throughput 則の 7〜9 倍あった（78〜117 回 対 9〜15 回）。
   - しかし分割ありの判定は 2〜5 倍、延べ数は 1.5〜2.9 倍にとどまった。
   - quality 則の 1 エポックでは、イベントの 98% が最初の 25% に集中した。小さいバッチの初期の判定ほど、多くの重心が閾値を下回る。
5. **separated で復活が効く理由とも整合する（結論 3 の裏付け）。**
   - separated の標的は 100% が共有ブロブ上で、単独の重心を剥がした例はなかった。
   - 学習後の未被覆ブロブは、復活なしの 95〜102 から 64〜81 に減り、Lloyd++25（93）より少なくなった。
   - ただし、寄贈元の 92% は単独の重心で、子は寄贈元と同じブロブの上に置かれる。その後どのように未被覆のブロブへ移るかは記録していない（未検証）。

## 再現コマンド

```bash
P="uv run python diagnose_revival.py --profile medium --threads 4"
$P --dataset imbalanced --imbalance-exponent 1.0 --run-name rev_imb10
$P --dataset imbalanced --imbalance-exponent 1.3 --run-name rev_imb13
$P --dataset separated --run-name rev_sep
for law in quality throughput; do
  $P --dataset imbalanced --dim 2 --seeds 0 1 2 --batch-law $law --run-name rev_d2_$law
done
```

既定は 5 シード、1 / 3 / 10 エポック、閾値 0.1 と 0、Lloyd++25 の参照付き。生のイベント列（`results/<run>/events.csv`、`checks.csv`）は Git 管理外で、本文の「最初の 25%」などはここから集計した。

## 次の検証候補

- 初期の EMA 質量が真の大きさに追いつかないことが主因かを確かめる。例えば、最初の数回の判定だけ復活を止める。公式コードは改変せず、外側から `begin` / `accumulate` / `update` を使う。
- 閾値を 0.001〜0.05 で細かく振る（[findings-imbalanced.md](findings-imbalanced.md) の候補を継続）。
- separated で、復活させた子が未被覆のブロブへ移る経路を追う（判定後の子の位置の追跡）。
